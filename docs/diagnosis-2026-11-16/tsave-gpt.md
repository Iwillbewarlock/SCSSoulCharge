[추정] 다음은 **팩토리 직접 생성 부분을 대체할 핵심 경로만** 보여주는 스케치입니다. 함수 이름은 확실하지만 로컬 헤더 대조·컴파일·소유권 검증은 미확인입니다. `effectDefs`에는 현재 시험과 동일한 효과 정의를 전달한다는 전제입니다.

```cpp
RE::EnchantmentItem* CreateManagedProbe(
    RE::BSTArray<RE::Effect*>& effectDefs)
{
    auto* manager = RE::BGSCreatedObjectManager::GetSingleton();
    if (!manager) {
        return nullptr;
    }

    auto* enchantment = manager->CreateWeaponEnchantment(effectDefs);
    if (!enchantment) {
        return nullptr;
    }

    // [추정] 시험용 보유 참조 한 개.
    // 로드 때마다 반복하지 않으며, 장기 회수 정책은 별도 검증합니다.
    manager->IncrementEnchantmentReference(enchantment);
    return enchantment;
}
```

[추정] 이 스케치 다음에 기존 staff용 `data` 설정을 적용하려면 반환 객체를 독점적으로 수정해도 되는지 먼저 확인해야 합니다. 효과 입력의 복제·소유권도 확인하기 전에는 임시 `Effect`들을 임의로 해제하면 안 됩니다. 이 코드는 완성된 제품 패치가 아닙니다.

[추정] 자동 판정은 다음처럼 구성하면 “같은 ID가 출력됐다”와 “효과가 실제로 복원됐다”를 구분할 수 있습니다.

| 시점 | 기록·검사 |
|---|---|
| 저장 전 | 프로세스별 nonce, 원본 주문 ID, 제작 인챈트 ID, **순서가 있는 효과 정의 8개의 서명**을 기록합니다. 서명에는 `baseEffect` ID와 magnitude/area/duration을 포함합니다. |
| 저장 전 | 해당 인챈트에서 발생한 ActiveEffect 7개를 원본 효과 인덱스와 연결해 기록합니다. 각 효과의 `elapsedSeconds`, `duration`, `magnitude`도 저장합니다. |
| co-save load callback | 저장 ID를 `ResolveFormID()`로 해석하고 기대 상태를 읽습니다. 이 시점의 성공만으로 PASS를 내지 않습니다. |
| `kPostLoadGame` | **POOL 재생성·슬롯 재바인딩·재시전 전에** 레지스트리의 폼 타입, 효과 정의 8개, ActiveEffect 7개와 각각의 상태를 비교합니다. |
| 다음 게임 업데이트 | 초기 로드 후 정리 과정에서 효과가 다시 탈락하지 않았는지 한 번 더 확인합니다. |

[추정] 전체 ActiveEffect 수 `578`이나 `592`는 판정 기준으로 삼지 마십시오. 해당 소스의 일곱 효과를 식별해 비교해야 합니다. 저장 이벤트와 실제 직렬화 사이의 시간차를 고려해 elapsed에는 짧은 허용 오차를 두되, 약 `6.6`초였던 값이 `0`으로 초기화되는 재시전은 실패로 판정해야 합니다.

[추정] 최종 PASS 조건은 다음 모두입니다.

- 저장한 프로세스 nonce와 현재 nonce가 달라 **실제 재시작 시험**임.
- 제작 인챈트가 플러그인의 사후 재생성 없이 존재하며 효과 정의가 일치함.
- 7개 효과가 대응되는 정의에 연결되고, 경과 시간·지속 시간·위력이 일치함.
- 보정 시전 횟수가 0이며 다음 업데이트에서도 유지됨.

[추정] 권장 성공 출력 예시는 다음과 같습니다. **실측 결과는 아닙니다.**

```text
T-SAVE-COLD PASS cold=1 formOK=1 definitions=8/8
active=7/7 stateMatch=1 repairCasts=0 survivedNextUpdate=1
```

[추정] 폼은 있으나 효과 목록이 비었다면 `FAIL reason=SOURCE_EFFECTS_MISSING`, 폼 조회부터 실패하면 `FAIL reason=SOURCE_FORM_MISSING`으로 분리하십시오. 시험 기록이 없는 모드 설치 전 저장에는 `NOT_RUN`을 출력하십시오. 같은 프로세스 A→B→A와 별도의 새 프로세스에서 A/B 로드를 모두 통과해야 이 문제의 수정으로 판정할 수 있습니다.
